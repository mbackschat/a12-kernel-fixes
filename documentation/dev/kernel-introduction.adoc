= Introduction

[#functionality]
== Functionality

Kernel is the model-driven logic core of the A12 platform.
It owns the Document Model — the definition of an application's document structures — and the documents that instantiate it, and it evaluates the business rules modeled on them:
plausibility checks (validation) and derived values (computation), authored manually by modelers in the Kernel Language inside the Document Model.

Kernel compiles these modeled rules into executable code and evaluates them over documents.
Because Kernel provides implementations for both the server (Java, Groovy) and the client (TypeScript), the rules modeled in the Document Model apply identically everywhere — the same validation a user sees while typing in a form is enforced when the document is stored.

Beyond rule evaluation, Kernel provides the Document API for working with documents programmatically, model fragment reuse (Combination Model), mapping of data from source models onto a target model, and model migration.

Kernel covers the document side of A12 data modeling;
the remaining elements — Relationship Models and links — are established outside Kernel.

Kernel is neither a server nor a user-interface component:
it is a library embedded by nearly every other A12 component and by application code on both sides of the wire.

Kernel does not author the rules it evaluates:
Document Models and their Kernel Language rules are written with the Simple Model Editor (SME).
It does not store documents — that is Data Services — and it does not establish relationships:
Relationship Models are likewise authored with the SME, links are persisted by Data Services, and relationship editing in the user interface is the Relationship Engine.
Forms and other user interfaces are rendered by the client engines, and read-only display composites of field values use the separate Expression Language of the Expression component, not the Kernel Language.

[#architecture]
== Architecture

Kernel is a library with twin implementations (not a deployable application) of the same model-driven contract
— Java for the server side, TypeScript for the client side.
Parity is a property of the code generated from the models: validation and computation behave identically in Java, TypeScript, and Groovy, while mapping is generated for Java and Groovy (there is no mapping on the client).
The core builds on Base and the A12 Utils packages; no A12 server is required.
Kernel, those libraries, and a project's own extensions all run inside the process that embeds them; none of them is a service.

Its main building blocks:

* *Kernel Language compilation* — parses the validation and computation rules authored in a Document Model and generates executable code from them (Java, TypeScript, or Groovy).
* *Runtime services*
** execute *validation* and *computation* over documents using the generated code.
  Validation runs in full (the entire document) or partially (for example, a single page before the user proceeds), with the same rules in both modes.
** *Mapping* — a separate runtime service that maps data from one or more source models onto a target model (structural mapping), available on the server side only, in Java and Groovy.
* *Document API* — programmatic creation and manipulation of documents with immutable, copy-on-write semantics.
* *Combination Model* — reuse of model fragments, which avoids duplicate modeling work and produces the Document Model the runtime works with; a Combination Model may also serve as a source for a mapping.
* *Model migration* — a module with a command line interface for migrating models.
* *Two service configurations* — dynamic (rule code is generated on demand and cached) or static (rule code is pre-generated ahead of time and shipped with the application); the distinction applies to mapping as well.

Beyond these, Kernel provides model search and model manipulation services that are platform-internal rather than project-facing.

Its extension points are exactly two: *Custom Field Type* and *Custom Condition*.
Each is provided by the project, obtained from a factory by name, and implemented in both Java and TypeScript.

WARNING: Code generated by an older Kernel version is not supported and throws at runtime.
See <<Getting started using code generated by Kernel at runtime>>.

API stability tiers are described in the <<Breaking Change Management>> chapter.

[#artifacts]
== Artifacts

Only a small, curated set of artifacts is Kernel's public dependency surface; the rest of the repository is internal.
Kernel publishes for both ecosystems — Maven for Java, npm (scope `@com.mgmtp.a12.kernel`) for TypeScript:

[cols="2,3"]
|===
| Artifact | Purpose

| `kernel-md-facade` (Maven and npm)
| The recommended default dependency, and for TypeScript the entry point to every public API: validation, computation, documents, and the model services.

| `kernel-md-serializer` (Maven)
| (De)serialization of documents and Document Models only (without the transitive dependencies of generated rule code).
  Arrives with `kernel-md-facade`; declare it directly only for that narrow need.

| `kernel-md-document-v2` (Maven)
| The immutable document data types, kept deliberately dependency-lean so that a project working only with documents can declare it directly.
  Otherwise it arrives with `kernel-md-facade`.

| `kernel-core-customfieldtype-api` (Maven)
| The Java API for implementing custom field types and custom conditions; arrives with `kernel-md-facade`.

| `kernel-core-runtime-api-ts` (npm)
| The TypeScript counterpart for custom code; arrives with kernel-md-facade.
|===

[#technologies]
== Technologies

* Java and TypeScript as the two implementation languages; Groovy as an additional code-generation target.
* Delivered via Maven and npm.
* No runtime infrastructure of its own — Kernel runs inside the process of whatever embeds it.

[#terminology]
== Terminology

[cols="1,3"]
|===
| Term | Meaning

| Document Model
| The model defining an application's document structures and the rules on them.
  Together with Relationship Models, Document Models form the application's data model.

| Kernel Language
| The language in which validation and computation rules are authored inside a Document Model.
  Not to be confused with the Expression Language of the Expression component, which serves read-only display.

| Document API
| The programmatic interface for creating and manipulating documents; documents are immutable, and every change produces a new copy.

| Validation
| Evaluation of the modeled plausibility checks over a document — in full, or partially (for example, per page).

| Computation
| Evaluation of the modeled rules that derive field values from other fields.

| Mapping / Structural Mapping
| The mapping of data from one or more source models onto a target model, executed by the mapping service on the server side.

| Dynamic / static configuration
| Whether the executable rule code is generated on demand at runtime (and cached) or pre-generated at build time and shipped with the application.
|===
